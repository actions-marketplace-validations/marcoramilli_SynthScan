# SynthScan — Machine-Readable System Description

> This document is written for an LLM agent that needs to understand, reproduce,
> extend, or build a compatible system. It describes every design decision,
> algorithm, data structure, and extension point in SynthScan v2.0.

---

## 1. Purpose

SynthScan is a static-analysis tool that estimates how much of a source-code
repository was generated by an AI assistant. It produces a normalised score
(the **Synthetic Code Score**, per 1 000 lines of code) and a detailed per-file,
per-category breakdown. It runs as a GitHub Action and can also be executed
locally as a standalone Python script.

## 3. Core Concepts

### 3.1 Pattern

A pattern is a single detection rule. It has:

| Field | Type | Description |
|-------|------|-------------|
| `category` | str | Logical group (e.g. "AI Slop Vocabulary") |
| `raw` | str | The actual pattern string |
| `is_regex` | bool | Whether to compile as a Python regex |
| `severity` | str | One of CRITICAL / HIGH / MEDIUM / LOW |
| `compiled` | re.Pattern | Pre-compiled regex object (None for plain-text) |
| `applies_to` | frozenset[str] | File extensions this pattern fires on (None = all) |
| `excludes_from` | frozenset[str] | File extensions this pattern is suppressed on |

Plain-text patterns are matched case-insensitively as substrings. Regex patterns
use `re.search()` (partial match anywhere on the line).

### 3.2 Match

A match is one fired pattern instance in one file. It records:

| Field | Type | Description |
|-------|------|-------------|
| `file` | str | Absolute path to the source file |
| `line_number` | int | 1-based line number (0 for cross-file hits) |
| `line_text` | str | The source line, capped at 200 chars |
| `pattern_raw` | str | The pattern that fired |
| `category` | str | Category of the pattern |
| `severity` | str | Severity of the pattern |
| `score` | float | Effective score after context multiplier |
| `context` | str | "COMMENT", "STRING", or "CODE" |
| `clustered` | bool | True if score was boosted by the clustering pass |

### 3.3 ScanResult

Aggregated result of scanning an entire directory tree:

| Field | Type | Description |
|-------|------|-------------|
| `total_score` | float | Sum of all match scores (after all adjustments) |
| `matches` | list[Match] | All matches across all files |
| `lines_scanned` | int | Total LOC counted (or added LOC in diff mode) |
| `files_scanned` | int | Number of source files processed |
| `by_directory` | dict[str, float] | Per-directory score totals |
| `synthetic_code_score` | property | `total_score / lines_scanned * 1000` |
| `high_critical_hit_rate` | property | HIGH+CRITICAL count / files_scanned |

## 4. Scoring System

### 4.1 Severity → Points

| Severity | Points |
|----------|--------|
| CRITICAL | 10 |
| HIGH | 5 |
| MEDIUM | 2 |
| LOW | 1 |

### 4.2 Context Multiplier (applied per line match)

| Context | Multiplier | Rationale |
|---------|-----------|-----------|
| COMMENT | ×1.5 | AI writes more slop in comments than in code |
| CODE | ×1.0 | Baseline |
| STRING | ×0.5 | String literals may be intentional user-facing copy |

Context is determined per-line by tracking multi-line string delimiters (`"""`,
`'''`) and single-line comment prefixes (`#`, `//`, `/*`, `*`).

### 4.3 Clustering Bonus

After scanning a file, matches are sorted by line number. If 3 or more matches
fall within a 10-line window, each match in that window has its score multiplied
by ×1.5 and is flagged `clustered=True`. Dense clusters of AI tells carry much
more signal than isolated hits.

Implementation: `apply_clustering(matches: list[Match]) -> list[Match]`

Parameters:
- `CLUSTER_WINDOW = 10` (lines)
- `CLUSTER_MIN_HITS = 3`
- `CLUSTER_MULTIPLIER = 1.5`

### 4.4 Diminishing Returns

If a single file generates more than 20 matches, all matches beyond the 20th
(sorted descending by score) are discounted to ×0.5. This prevents one large
AI-generated file from making the repo-level score uninterpretable.

Parameters:
- `DIMINISHING_RETURNS_THRESHOLD = 20`
- `DIMINISHING_RETURNS_FACTOR = 0.5`

### 4.5 Normalised Score

$$\text{Synthetic Code Score} = \frac{\text{Raw Score}}{\text{Lines Scanned}} \times 1000$$

Reference thresholds (empirically derived):
- 0–5 → likely human-written
- 5–15 → low AI signal
- 15–30 → moderate AI signal
- 30+ → strong AI signal

## 5. Detection Layers

### 5.1 Line-Level Pattern Matching (`scan_file`)

**Function signature:**
```python
def scan_file(
    filepath: Path,
    patterns: list[PatternDef],
    diff_lines: set[int] | None = None,
) -> list[Match]
```

For each line in the file:
1. Determine context (COMMENT / STRING / CODE).
2. If `diff_lines` is set, skip lines not in `diff_lines`.
3. Skip lines containing `synthscan: ignore` (inline suppression).
4. For each pattern:
   - Skip if `pat.applies_to` is set and the file extension is not in it.
   - Skip if `pat.excludes_from` is set and the file extension IS in it.
   - Skip if the file is a documentation file (`.md`, `.txt`, `.rst`, `.adoc`,
     `.rdoc`) and the pattern category is in `SOURCE_ONLY_CATEGORIES`.
   - Test the line: regex `re.search` or case-insensitive substring.
   - If hit: create Match with `score = base_score * context_multiplier`.

`SOURCE_ONLY_CATEGORIES` (suppressed on doc files):
- Slop Phrases
- AI Slop Vocabulary
- Verbosity Indicators
- Example Usage Blocks
- Redundant / Tautological Comments
- Self-Referential Comments

### 5.2 Multi-Line Block Detection (`scan_file_blocks`)

Reads the full file text and applies three structural detectors:

**Detector A — AI-structured docstrings**
Finds triple-quoted strings containing ≥ 3 of these section headers:
`args:`, `parameters:`, `returns:`, `yields:`, `raises:`, `notes:`, `examples:`, `attributes:`
Score: HIGH (5 pts), context STRING.

**Detector B — Bare try/except wrapping**
Regex: a function whose entire body is `try: ... except Exception`.
Score: MEDIUM (2 pts), context CODE.

**Detector C — Over-commented blocks**
Scans 20-line windows; if > 50 % of lines are comments, flags the block.
Score: LOW (1 pt), context COMMENT.

### 5.3 AST Structural Analysis (`scan_file_ast`, Python only)

Parses the file with `ast.parse()`. Detects:

**Unreachable code** — statements after `return`/`raise` inside function bodies
(excluding trailing string-literal docstrings). Category: "Dead Code", MEDIUM.

**Deep nesting** — functions where `_max_nesting_depth()` > 3. Counts `if`,
`for`, `while`, `try`, `with` nodes recursively. Category: "Deep Nesting", LOW.

**Unused imports** — import names that do not appear as `ast.Name` or
`ast.Attribute` nodes anywhere in the file. Category: "Unused Imports", LOW.

**Result-variable anti-pattern** — the last two statements of a function are
`<generic_name> = expr` followed by `return <generic_name>`, where generic
names are: `result`, `output`, `response`, `data`, `ret`, `rv`, `value`,
`res`, `processed`, `out`. Category: "AI Structural Patterns", LOW.

**Over-parameterized function** — more than 7 optional arguments with defaults
(`args.defaults + non-None kw_defaults`). Category: "AI Structural Patterns", LOW.

### 5.4 Fuzzy Cross-File Repetition (`detect_cross_file_repetition`)

After walking the entire directory tree, a registry of normalised docstrings is
built: `{normalised_text: [file_path, ...]}`. Normalisation: lowercase + collapse
whitespace.

Grouping uses union-find with token-level Jaccard similarity:

$$J(A, B) = \frac{|A \cap B|}{|A \cup B|}$$

where A and B are the token sets of two docstrings. If J ≥ 0.85, the two
docstrings are merged into the same group.

If a group covers ≥ 3 distinct files, every file in the group receives a match:
Category "Cross-File Repetition", HIGH (5 pts), line 0 (file-level).

Parameters:
- `REPETITION_MIN_FILES = 3`
- `REPETITION_SIMILARITY_THRESHOLD = 0.85`

## 6. Pattern File Format (`synthetic_patterns.md`)

The pattern file is a Markdown document. The parser (`load_patterns`) interprets
the following structure:

```markdown
## Category Name

Default severity: **HIGH**

Applies to: .py, .js
Excludes: .md, .txt

```patterns
# This is a comment, ignored by the parser
plain text pattern (minimum 10 chars)
regex:python_regex_pattern
[CRITICAL] regex:override_severity_pattern
```
```

**Rules:**
- `## Category Name` resets current category, severity, applies_to, excludes_from.
- `Default severity: **LEVEL**` sets the category default (outside code blocks).
- `Applies to: .ext1, .ext2` scopes the category to those file extensions.
- `Excludes: .ext1, .ext2` suppresses the category on those file extensions.
- Lines inside `\`\`\`patterns` blocks are parsed as patterns.
- Lines starting with `#` inside pattern blocks are comments (ignored).
- Lines starting with `regex:` are compiled as Python regular expressions.
- Lines with `[CRITICAL]`, `[HIGH]`, `[MEDIUM]`, or `[LOW]` prefix override
  the category default severity for that one pattern.
- Plain-text patterns shorter than 10 characters are rejected.
- Invalid regexes are skipped with a warning to stderr.

## 7. Supplementary Features (v2.0)

### 7.1 Diff / PR Mode

**Activation:** set `INPUT_DIFF_FILE` environment variable to the path of a
unified diff file (e.g. output of `git diff HEAD~1`).

**Behaviour:**
- `parse_unified_diff(diff_text)` returns `{relative_path: {added_line_nos}}`.
- `scan_directory` skips files not in the diff map entirely.
- `scan_file` receives `diff_lines` and skips non-added lines during pattern
  matching. Multi-line block detection and AST analysis still run on the full
  file (for structural context).
- `lines_scanned` counts added lines only; score normalises against diff LOC.

### 7.2 `.synthscanignore` / Inline Suppression

**`.synthscanignore`:** gitignore-style glob patterns (one per line). Loaded
by `load_ignore_patterns(path)`. Matching uses `re.search` on the file's
workspace-relative path. Glob conversion: `**` → `.*`, `*` → `[^/]*`, `?` → `[^/]`.

**Inline suppression:** any line containing `synthscan: ignore` (case-insensitive)
is skipped entirely during `scan_file` pattern matching.

**Activation:** set `INPUT_IGNORE_FILE` environment variable (default:
`.synthscanignore` in the working directory).

### 7.3 SARIF Output

**Activation:** set `INPUT_SARIF_OUTPUT=true`.

`write_sarif(result, repo_root, output_path)` emits a SARIF 2.1.0 document
compatible with GitHub Code Scanning (`github/codeql-action/upload-sarif`).

SARIF severity mapping:
- CRITICAL → `error`
- HIGH → `error`
- MEDIUM → `warning`
- LOW → `note`

Each match with a non-zero line number becomes a SARIF result with a
`physicalLocation` pointing to the file and line. Cross-file repetition hits
(line 0) are omitted from SARIF (file-level only).

Rule IDs are derived from category names with `re.sub(r"[^a-zA-Z0-9/_.-]", "-", category)`.

## 9. GitHub Action Interface

### Inputs

| Name | Default | Description |
|------|---------|-------------|
| `scan_path` | `.` | Directory to scan |
| `patterns_file` | `patterns/synthetic_patterns.md` | Pattern file path |
| `score_threshold` | `0` | Fail if score ≥ value (0 = never) |
| `create_issue` | `true` | Create/update GitHub Issue |
| `issue_label` | `synthscan` | Issue label |
| `report_path` | `synthscan-report.json` | JSON report path |
| `diff_file` | `""` | Unified diff file path (activates PR mode) |
| `sarif_output` | `false` | Emit SARIF report |
| `ignore_file` | `.synthscanignore` | Ignore file path |

### Outputs

| Name | Description |
|------|-------------|
| `score` | Synthetic Code Score (per 1k LOC) |
| `raw_score` | Un-normalised total score |
| `match_count` | Number of pattern matches |
| `lines_scanned` | Total LOC scanned |
| `issue_body` | Full Markdown report |
| `high_critical_hit_rate` | HIGH+CRITICAL hits per file |
| `by_directory` | JSON object: directory → score |
| `sarif_path` | SARIF report path (if `sarif_output=true`) |

### Environment Variables (for local execution)

The script reads all inputs as `INPUT_*` environment variables:
`INPUT_SCAN_PATH`, `INPUT_PATTERNS_FILE`, `INPUT_SCORE_THRESHOLD`,
`INPUT_REPORT_PATH`, `INPUT_DIFF_FILE`, `INPUT_SARIF_OUTPUT`,
`INPUT_SARIF_PATH`, `INPUT_IGNORE_FILE`.

GitHub Action outputs are written to `$GITHUB_OUTPUT` in key=value format.
Multi-line values (issue_body) use the heredoc syntax:
```
issue_body<<EOF_SYNTHSCAN
...content...
EOF_SYNTHSCAN
```

## 11. Extending the System

### Adding a New Pattern Category

1. Append a new `## Category Name` section to `patterns/synthetic_patterns.md`.
2. Optionally set `Default severity:`, `Applies to:`, or `Excludes:`.
3. Add patterns in a `\`\`\`patterns` fenced block.
4. No code changes required — patterns are loaded dynamically at runtime.

### Adding a New AST Detector

1. Add logic inside `scan_file_ast()` in `scanner/synthscan.py`.
2. Use a new or existing category name.
3. Append `Match` objects to `ast_matches`.
4. The rest of the pipeline (clustering, diminishing returns, output) handles
   AST matches identically to line-level matches.

### Adding Support for a New Language's AST

Currently AST analysis is Python-only. To add another language:
1. Add a new function `scan_file_ast_<lang>(filepath)` that shells out to a
   language-specific parser or uses an in-process library.
2. Call it conditionally in `scan_directory` based on `fpath.suffix`.
3. Return `list[Match]` objects with the same structure.

### Adding a New Output Format

1. Add a new writer function `write_<format>(result, repo_root, path)`.
2. Wire a new environment variable (`INPUT_<FORMAT>_OUTPUT`) in `main()`.
3. Add a corresponding GitHub Action input in `action.yml`.

## 12. Known Limitations and False-Positive Risks

| Limitation | Notes |
|-----------|-------|
| Vocabulary patterns are language-agnostic | Words like `robust`, `seamless`, `leverage` appear in legitimate technical prose. They are scoped to COMMENT context to reduce FPs. |
| AST analysis is Python-only | JavaScript, TypeScript, Go, etc. have no AST layer. |
| Cross-file repetition is file-path-deduped | The same file can appear multiple times in the registry if it has several matching docstrings. |
| Diff mode block/AST detection | Block and AST detectors run on the full file, not just diff lines. This may flag pre-existing issues in modified files. |
| Pattern min-length of 10 chars | Short plain-text patterns are rejected to avoid trivial substring FPs. |
| No ML layer | The detection is entirely rule-based. High-quality AI-generated code that avoids all known tells will score low. |

## 13. Design Principles

1. **Zero dependencies** — the scanner must run with `python3 scanner/synthscan.py`
   on any GitHub Actions runner without a separate install step.
2. **Editable patterns** — all detection logic lives in the Markdown file, not in
   code, so non-engineers can add and tune patterns.
3. **Normalised score** — raw score divided by LOC makes results comparable across
   codebases of different sizes.
4. **Opt-in strictness** — `score_threshold=0` never fails the build; teams adopt
   the tool before enforcing it.
5. **Context awareness** — the same pattern scores differently in a comment vs.
   a string literal vs. active code.
6. **Graceful degradation** — malformed files (encoding errors, AST parse
   failures, OS errors) are silently skipped rather than crashing the scan.
